# 数据采集手册

助手不向游戏发包，也不自己扫图。它只监听本机已经收到的游戏流量：游戏服务器从 TCP 8001 推下来的包，解密后写入 `capture_new/`，再进当前服务器对应的 SQLite 库 `stzb_<服务器IP>.db`。

你在游戏里没打开、没请求过的界面，助手里就不会有那份数据。库是累积的，重启不会清空；但已经进库的战报也不会被后来的同号战报覆盖。

## 1. 先把采集跑起来

1. 启动 Web：`python run_web_exe.py --no-browser`。默认会同时拉起抓包线程。`--no-sniffer` 只看旧库，不再收新包。
2. macOS 上抓包要能读到游戏网卡流量。权限不够时页面仍能打开，日志里是抓包线程启动失败，库不会增加新行。
3. 登录游戏并进入城池。抓到第一包就按服务器 IP 建目录；随后用角色包（`0x1395`，含 `role_id` / 角色名）或主公簿包（`0xe6`）把目录绑到当前账号，并写入 `current_profile.json`。
4. 右上角角色名和服务器 IP 正确之后，再按下面的清单在游戏里点一次。点之前的历史包不会补进战报库。

报文按命令号分目录，例如 `capture_new/<账号>/000013a2/`。入库有两条路：

| 路径 | 何时发生 | 覆盖的命令 |
|---|---|---|
| 实时入库 | 抓到包立刻解析 | 地图 5026/5028、个人战报 10、同盟战报 92、同盟成员 103、赛季战绩 510，以及旧地图格 |
| 文件扫描 | 后台约每 1.5 秒扫新 JSON | 上面这些，再加上 90005 队伍表、聊天、公告、武将记录、攻城相关包 |

重启时，扫描器会把目录里已经存在的 JSON 标成已处理，不再重放。所以战报必须在抓包进程活着的时候打开。90005 是例外：打开「我的队伍」时还会把尚未投影过的 `00015f95` 文件补进库。

## 2. 刚开始的初始化清单

按这个顺序做一遍，空库就能有第一份可用数据。每一项都要等游戏自己把包拉回来，助手不能代请求。

| 顺序 | 在游戏里做 | 拿到什么 |
|---|---|---|
| 1 | 登录，进自己的城 | 账号绑定；90005 开始推自己的 `Tb_army` / `Tb_hero` |
| 2 | 打开世界地图，在要看的区域停几秒，再拖到下一块 | 该矩形的 5026 底稿。只停在一处，就只有那一块 |
| 3 | 打开个人战报，翻完要保留的页 | 命令 10，写入 `battles_v2`。这是「我的队伍」战报认领的来源 |
| 4 | 打开同盟战报 | 命令 92，同一张战报表，范围是同盟战报 |
| 5 | 打开同盟成员 | 命令 103，成员、贡献、武勋、分组、主城坐标 |
| 6 | 打开赛季历程 / 个人战绩 | 命令 510，城池数、土地数、武勋、击杀 |
| 7 | 有攻城时打开对应城池或加速界面 | 城池动态、队列快照 |

做完后刷新助手页面。地图只会出现你停留过的矩形里、服务器实际下发的格子；战报只会出现这次打开的列表里带有的 `battle_id`。

## 3. 地图：初始化是一块，增量是停在这块上的变化

世界场景是一条链路：游戏用 5025 按当前镜头请求一块矩形，服务器用 5026 回这块的全量，之后用 5028 推这块上的变化。助手只收得到 5026 和 5028。

命令号：

- `000013a2` / 5026 `SEND_WORLD_SCENCE_FULL_INFO`：当前观测范围的底稿。
- `000013a4` / 5028 `SEND_WORLD_SCENCE_CHANGE_INFO`：底稿之后的增量。

5026 可能分多帧。中间帧的序号槽是 0，只拼进缓存；最后一帧序号大于 0，才整包写入。序号不大于上一份已完成 5026 的 5028 会被丢掉。特殊序号 `-999999999` 可以绕过这道门。

一份 5026 的权威范围是包里的 `observedMapArea`（第 17 槽，`上、下、左、右`），不是整张服的地图。这个矩形通常一边几百格，比助手里 20×20 的战术镜头大，但仍然只是你当时镜头附近。

初始化：

- 打开世界地图并在目标区域停留，直到日志出现完整 5026。
- 这一帧会写入城池/地标（chunk `0`，表 `world_tiles`）、土地块（含 chunk `8` 的土地等级）、地图上的部队、同盟名、以及当时可见的实时行军。
- 同一矩形里，这次包没有再带上的城池行会被删掉。矩形外面的旧数据保留。
- 5026 的实时行军是整表替换：这一帧没出现的行军会从 `world_real_marches` 清掉。

增量：

- 停在地图上时，部队移动、城池状态、土地块变化走 5028。5028 只覆盖包里出现的对象，不会因为没提到某格就删掉它。
- 5028 的实时行军只叠加，不整表清空。
- 离开该区域再回来，会再来一份新的 5026，那块矩形重新以新底稿为准。

土地颜色只来自 chunk `8`。服务器没下发的格子保持空白，不代表定位错了，也不代表那格在游戏里没有等级。要塞、营垒名字来自 chunk `0` 的城池行，和土地等级是两套数据。

WID 换算：`行 = wid // 10000`，`列 = wid % 10000`。

地图采集做不到的事：

- 不打开、不拖动游戏镜头，就没有那一块。
- 助手页面上的定位、缩放不会向游戏要数据。
- 一次登录不会自动铺满全图。要哪一带的土地等级，就得把游戏镜头移到那一带再停一会儿。

## 4. 战报：打开列表才入库，同一场只收第一次

战报不是地图那种推送底稿。完整战报来自你打开战报页时的请求回包。

| 命令 | 十进制 | 客户端名 | 游戏里怎么来 | 入库 |
|---|---:|---|---|---|
| `0000000a` | 10 | `GET_ALL_BATTLE_REPORT_PROFILE_CMD` | 打开个人战报 | `battles_v2`、`battle_heroes`、武勋、势力、考勤 |
| `0000005c` | 92 | `GET_UNION_BATTLE_REPORT` | 打开同盟战报 | 同上，同一套表 |
| `00000834` | 2100 | `NOTIFY_CHAT_MSG` | 聊天推送；其中一类会被认成战斗通知 | 聊天写入 `chat_messages`。战斗通知只弹事件，不进战报表 |

一条战报进库后保存：双方名字、同盟、时间、胜负、坐标和地名、兵力与剩余、武将等级和红度、`all_skill_info` 里的战法。个人战报和同盟战报格式不同，解析后都落到 `battles_v2`，用 `battle_id` 区分。

更新规则：

- 同一个 `battle_id` 只插入一次。后来又打开战报、拿到同一场的更完整内容，直接丢弃，不会补战法、兵力或红度。
- 所以第一份必须是打开战报列表时的完整包。只收到 834 通知时，库里还没有这场。
- 新打完的战斗不会自动变成完整战报。要再打开一次个人战报或同盟战报，列表里出现的新 `battle_id` 才会进来。
- 列表是游戏这次返回的那些场，不是服务器上的全部历史。没翻到、没返回的场次，库里没有。
- 重启不会把旧报文重新导入战报。漏抓的只能再打开游戏战报；若那场 `battle_id` 已经以残缺内容进库，再打开也不会覆盖。

「我的队伍」里的战报队伍，是用当前 `current_profile.json` 的角色名，精确匹配 `battles_v2` 的攻方名或守方名。角色名没绑上时，这条认领是空的。它不是城池界面的实时编制。

## 5. 自己的编制：90005，登录就推，之后按字段改

| 命令 | 十进制 | 客户端名 | 含义 |
|---|---:|---|---|
| `00015f95` | 90005 | `SYS_NOTIFY_DB_UPDATE_90005` | 客户端数据表变更通知 |

这是服务器推送，不用点城池。登录后会推一批，之后改队伍、征兵、换战法时再推变更。

一条记录是 `[操作, 表名, 行数据]`。操作 `1` / `2` 写入或更新，`3` 删除。整行和稀疏字段更新都会合并进 `own_sync_rows`。

和队伍有关的只有两张表：

- `Tb_army`：驻地、前排/中排/后排/参军、阵型、状态、城池类型。
- `Tb_hero`：武将、所属队伍、等级、体力、兵力、战法、红度、兵力上限。

其他表名会记在 `db_sync` 原始日志里，不投影成队伍。文件扫描约 1.5 秒入库一次；若当时没扫到，下次打开「我的队伍」会把目录里还没投影的 90005 文件补上。同名文件只投影一次，但表内容会随后到的更新包合并，这点和战报的「只收第一次」不同。

## 6. 其余会入库的数据

这些都要游戏自己发出对应回包。实时路径立刻入库的，重启前抓到就会在库里；只走文件扫描的，依赖抓包进程当时的扫描线程。

| 游戏操作 | 命令 | 客户端名 | 进哪 | 怎么更新 |
|---|---|---|---|---|
| 打开同盟成员 | `00000067` / 103 | `UNION_MEMBER_LIST` | `team_users` | 后来的成员包按 uid 覆盖名字、贡献、武勋、分组、坐标 |
| 打开赛季战绩 | `000001fe` / 510 | `USER_GET_USER_SEASON_COURSE` | `player_stats` | 按 userid 覆盖 |
| 打开地块/自身字段信息 | `00000015` / 21 | `GET_FIELD_INFO_CMD` | `player_self` | 覆盖名字、兵力、粮食、木材、移速、行军上限。只走文件扫描 |
| 打开公告 | `0000030c` / 780 | `NOTICE_LIST` | `announcements` | 按公告 id 覆盖。只走文件扫描 |
| 武将卡记录 | `0000029f` / 671 | `CARD_RECORD` | `hero_unlock_log` | 新记录插入，已有的忽略。只走文件扫描 |
| 聊天推送 | `00000834` / 2100 | `NOTIFY_CHAT_MSG` | `chat_messages` | 新消息插入。只走文件扫描 |
| 同盟建筑加速加入 | `000018aa` / 6314 | `UNION_BUILDING_SPEED_UP_ADD` | `battle_field` | 按城池 wid 覆盖攻击者和附近成员。只走文件扫描 |
| 攻城队列快照 | `000018ae` | 本仓库按队列解析，9.2.2 覆盖表没有正式名 | `battle_queue` | 按本次城池 id 重写队列。只走文件扫描 |
| 联盟榜 / 势力榜 | `000002bc` | 本仓库解析为联盟列表和玩家势力排行 | `union_list`、`player_power_rank` | 打开对应榜单时整批覆盖。只走文件扫描 |
| 战区玩家 | `00001863` | 本仓库解析为战区玩家列表 | `zone_players` | 打开对应列表时覆盖。只走文件扫描 |

周日更新同盟成员时，会额外记一份武勋快照，给定制积分用。

`0000012d` 会被文件扫描解析成一次行军打印，不进实时行军表。地图上会动的行军只认 5026/5028 第 29 槽。

## 7. 抓到了文件，也不等于页面上有

下面这些包会落在 `capture_new/`，当前 Web 业务页不用它们：

- 邮件、聊天历史、黑名单、小地图、任务、社区令牌、心跳 `90006`、登录 `99991`。
- `00000898` 通知包。扫描列表里已经注明废弃。
- 武将图鉴、战法表、头像。它们来自仓库里的配置和本地图片，不来自抓包。

页面是空的时候，先分清是哪一种：

- 右上角没有角色名：账号还没绑上，战报队伍无法认领。
- 地图一大片深色：镜头没到，或到了但服务器没下发土地等级块。
- 实时行军为空：当前 5026/5028 的第 29 槽没有行军。停在地图上才会刷新；5026 还会把上一份行军整表换掉。
- 战报缺战法：这场进库时 `all_skill_info` 就是空的。同 `battle_id` 再抓一次不会补。
- 重启后旧目录没有新战报：扫描器不重放启动前已经存在的 JSON。

## 8. 怎么确认这次抓到了

看进程日志里的这些行：

- `[bind]`：角色或服务器已识别。
- `[world_scene]` 或世界快照事件：5026 底稿完成，或 5028 增量写入。
- `[battle-0a]` / `[battle-5c]`：一场新战报入库。同一 id 再出现不会有第二行。
- `[team_users]`：同盟成员已覆盖。
- `[map]`：旧地图格解析到城池。

库文件是 `stzb_<服务器IP>.db`，和右上角服务器一致。换服务器会换库，旧服的战报和地图还在原来的文件里。
